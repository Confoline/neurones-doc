This part is for the people responsible for the platform's own proper operation: configuration, data retention, application instrumentation, external integrations, deployment, and backup.

## Settings {#settings}

The "Settings" page brings together five configuration areas, each as a clickable card:

| Card | Role |
|---|---|
| **OpenTelemetry Collector** | Manage the Collector configurations pushed to the agents installed on your infrastructure. |
| **Database Configuration** | Switch and manage the active Vertica / PostgreSQL / Oracle data sources. |
| **Data Retention** | Configure how long each data category is kept (details below). |
| **External CMDB Integration** | Connect and synchronize asset records with an external CMDB. |
| **External Event Management** | Forward the platform's events to an external incident management tool. |
{firstcol="30"}

## Data Retention {#retention}

Data retention determines how long each telemetry category is kept before automatic deletion — a trade-off between storage cost and how far back you can investigate. It's configured separately for each category, since their usefulness over time isn't the same:

| Category | Default | Range | Why |
|---|---|---|---|
| Spans (raw traces) | 30 d | 1–90 d | High-volume; mostly useful in the first days/weeks to investigate a specific incident. |
| Logs | 30 d | 1–90 d | Same profile as raw traces. |
| Metrics — 1 minute | 15 d | 1–30 d | Fine-grained analysis, used beyond a week during an in-depth investigation. |
| Metrics — 1 hour | 90 d | 7–180 d | Month-over-month trend comparisons. |
| Metrics — 1 day | 400 d | 30–730 d | Year-over-year comparisons. |
| Resolved events | 90 d | 1–730 d | Open or acknowledged events are never purged, no matter their age. |
{mono="2,3"}

For each area, the page shows a plain-language description, a real usage indicator (row count and estimated size), the day-count setting, an immediate-purge button (with confirmation), and a history of past purges.

{{< callout >}}
Disk size is an estimate; if it isn't available for a table, the row count is still shown, with an explicit note that the size is unknown rather than showing a false value.
{{< /callout >}}

An automatic purge runs once a day and applies the settings configured for each area. A purge can also be triggered manually at any time; either way, the action is logged with the date, the number of rows deleted, and the trigger source.

## Application Instrumentation (OpenTelemetry) {#otel}

For an application to appear in Neurons, it must be instrumented with OpenTelemetry and configured to export its traces and logs to the Collector. This section covers a common point of attention once basic instrumentation is in place: capturing HTTP headers and, more rarely, request/response bodies.

### Capturing HTTP headers

For security, OpenTelemetry captures no HTTP headers by default — headers frequently contain sensitive information (tokens, session cookies). Capture must be explicitly enabled, separately for inbound and outbound requests, and separately for the request and the response. This is done via environment variables for most backend languages; on the browser side, the same explicit list is declared in the instrumentation's JavaScript configuration.

{{< callout type="warn" >}}
Whatever the language, the same rule applies: never capture "all headers" — always use an explicit list, and always exclude authentication headers and cookies.
{{< /callout >}}

### Capturing request and response bodies

OpenTelemetry doesn't natively capture request or response content (the body) — only their size in bytes. Capturing the actual content requires custom instrumentation, enabled only for explicitly chosen routes, with two rules to always follow: limit the captured size, and mask sensitive fields before sending anything — there's no undoing it once the data has been exported.

## External Integrations {#integrations}

Two integrations connect Neurons to the rest of the operations ecosystem:

- **External CMDB** — synchronizes the consolidated list of applications, services, and business transactions with an external configuration management database.
- **External event management** — forwards the events generated by Neurons to an external incident management tool.

## Kubernetes Deployment {#k8s}

Neurons deploys as three independent components, each with its own image, grouped in the same Kubernetes namespace:

| Component | Role | Scaling |
|---|---|---|
| apm-ingest | Receives telemetry, runs the compute workers, and serves the query API. | The ingestion/query service scales horizontally; the 3 background workers stay single-instance. |
| neurones-backend | Control API: authentication, CMDB, Collector administration, real-time events. | Single instance. |
| neurones-frontend | Web application (dashboards, topology, settings), Next.js. | Scales horizontally. |
{mono="1"}

All three components rely on an external Vertica database and a small shared PostgreSQL control database. Both must exist and be reachable before starting the deployment.

### Things to watch before a first deployment

- A StorageClass supporting **ReadWriteMany** access is required for the shared GeoIP database volume — many default cloud storage classes (EBS, for example) don't allow it.
- The GeoIP database (MaxMind GeoLite2) isn't shipped in the published image for licensing reasons: each customer must generate their own license key.
- The {{< mono "neurones-backend" >}} PostgreSQL schema isn't applied automatically in production — an {{< mono "alembic upgrade head" >}} migration must be run explicitly before the first startup.
- The Vertica schema isn't applied automatically either: all migrations must be applied before apm-ingest's first startup.
- {{< mono "neurones-backend" >}} only accepts origins explicitly listed in its CORS configuration; forgetting this results in a frontend that renders but whose API calls all fail silently.
- {{< mono "neurones-frontend" >}}'s public URLs (API and WebSocket) are baked in at image build time, not at container startup.
- The ingestion buffer is in-memory only, with no durable queue behind it: size memory with headroom, and allow enough shutdown grace time during updates.
- The ingestion token is a single shared secret, not scoped per customer: treat it as sensitive and rotate it if it's ever exposed.

Once configured, a single script ({{< mono "deploy-neurons-apm.sh" >}}) handles the entire deployment, then waits until everything is ready. It can safely be re-run after a configuration change.

## Backup and Restore {#backup}

Neurons keeps its data in three places. They don't play the same role, and only two of them need a backup:

| Store | What it holds | Back it up? |
|---|---|---|
| **Vertica** (the "Data Lake") | All telemetry: traces, logs, browser events, session replays, the pre-computed summaries behind the dashboards, the workers' progress markers, alerting and incident history. | **Yes — critical.** It is the only copy of your history. |
| **PostgreSQL** | The configuration: users and access, settings, applications, health rules and notification policies, browser applications and their business fields, and which Vertica database the platform uses. | **Yes — small but critical.** Without it the platform doesn't work correctly, even with an intact Vertica. |
| **Kafka** (Kafka mode only) | The last hours of incoming traffic, before it is written to Vertica. | No — it is a temporary buffer. It does help after a restore (see below). |

The application images and the location database (GeoIP) are rebuilt with each deployment and don't need a backup.

### What to know before trusting a backup

- **The restore point is the last successful backup.** Plan the frequency around how much data you can afford to lose: nightly is a reasonable default, every 4 to 6 hours if you need more.
- **Back up both databases at the same moment** (within the same maintenance window), so that the configuration matches the data.
- **Direct mode:** anything ingested after the last Vertica backup is lost, and so are the few seconds of data still in memory if the ingestion service stops abruptly.
- **Kafka mode:** data ingested after the Vertica backup is still in Kafka for its retention period (24 h by default). The loader's position in the queue is saved *inside* Vertica, so after a restore it automatically resumes from the backup's position and reloads what came after. Data older than the Kafka retention is lost.
- **Keep backups off the machine.** Three destinations are supported for Vertica: S3-compatible object storage (recommended in production), an NFS network share, or local disk — local backups must then be copied to another machine, otherwise they don't protect against losing the server.

### Setting up the backups

**Vertica** is backed up with `vbr`, Vertica's backup tool, from the Vertica server:

```bash
vbr --setupconfig                          # once
vbr -t backup -c backup_config.ini         # a backup (to schedule)
vbr -t listbackup -c backup_config.ini     # list the backups
```

In the generated configuration, `restorePointLimit` sets how many backups are kept (for example `14` for two weeks of nightly backups).

**PostgreSQL** is backed up with `pg_dump`. In production a Kubernetes CronJob (`postgres-backup`) runs it every night at 02:30 (Paris time), checks that the file is not empty and is readable, and keeps 7 days of backups on its own volume. That volume is on the same server as the database: copy its files to another machine as well.

{{< callout type="warn" >}}
Make sure someone is warned when a backup fails or when the latest one is too old (for example more than 26 hours for a nightly backup). Discovering it during an incident is too late.
{{< /callout >}}

### Restore procedure

1. **Assess the damage.** Partial damage (one table, one time range) or total loss? When in doubt, treat it as total loss.
2. **Stop everything that writes:** the ingestion service, the loader (Kafka mode) and all the workers. In Kubernetes:

   ```bash
   kubectl -n <namespace> scale deployment apm-ingest apm-loader apm-worker \
     apm-trace-graph-worker apm-canonicalization-worker --replicas=0
   ```

3. **Restore PostgreSQL first** — the platform needs it to find its Vertica database:

   ```bash
   gunzip -c neurones-<date>.sql.gz | psql -h <host> -U <user> -d <database>
   ```

4. **Restore Vertica** from the last valid backup (or a named one):

   ```bash
   vbr -t restore -c backup_config.ini --archive <backup-name>
   ```

5. **Check the versions.** The restored databases must match the version of Neurons that is deployed: the last Vertica migration (`SELECT version FROM apm.flyway_schema_history ORDER BY installed_rank DESC LIMIT 1;`) and the PostgreSQL migration (`alembic current` in the backend). If the backup is older than the deployed version, run the migrations before restarting.
6. **Validate the data** before reopening the traffic:

   ```sql
   SELECT MAX(start_time) FROM apm.spans;
   SELECT MAX(start_time) FROM apm.rum_events;
   SELECT worker_name, checkpoint_name, last_bucket_time FROM apm.worker_checkpoints ORDER BY 1, 2;
   ```

   The most recent times tell you exactly where the backup stops.
7. **Restart** the ingestion service, the loader and the workers (`--replicas` back to their usual values). Each worker resumes from its own progress marker. In Kafka mode, watch the loader catch up on what Kafka still holds.
8. **Rebuild** what can be rebuilt for the missing period, if the raw data exists: the service dependency graph and the business transaction registry.
9. **Communicate** the exact time window that is missing, so nobody mistakes missing data for a quiet period.
{.steps}

{{< callout type="warn" >}}
A backup that has never been restored is not a verified backup. Restore the latest backups into a test environment every month, and run a complete, timed drill at least once a year — it gives you a real recovery time instead of an assumed one.
{{< /callout >}}
